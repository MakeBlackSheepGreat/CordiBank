# 技术文档

这份文档说明三件事：系统怎么分层，核心算法怎么工作，安全能力落在哪里。全部结论都能在源码里找到对应实现。

## 一、系统架构

### 分层

系统分五层，上层调下层，下层不反向依赖上层。

```mermaid
flowchart TB
  subgraph L1["入口层"]
    WEB["Web 控制台<br/>Vue 3 加 Vite"]
    IM["IM 渠道<br/>webhook 与企业微信"]
  end
  subgraph L2["协议层"]
    RPC["JSON-RPC 单入口<br/>方法名分发"]
  end
  subgraph L3["编排层"]
    SWARM["蜂群协同<br/>五角色加仲裁"]
  end
  subgraph L4["能力层"]
    TOOLS["工具注册表<br/>内置 21 个"]
    MCP["外部服务<br/>4 个服务 13 个工具"]
    SKILL["技能库<br/>按需加载"]
  end
  subgraph L5["数据层"]
    STATE["账户与账单<br/>整数分"]
    AUDIT["审计链<br/>SHA-256 前序哈希"]
  end
  WEB --> RPC
  IM --> RPC
  RPC --> SWARM
  SWARM --> TOOLS
  SWARM --> MCP
  SWARM --> SKILL
  TOOLS --> STATE
  SWARM --> AUDIT
```

分层规矩三条。

入口层只做收发，不判断业务。

编排层只做决策，不直接改数据，改数据一律经工具。

数据层对上层暴露读接口，写操作只能由工具执行。

### 五角色协同

一次对话的角色时序。

```mermaid
sequenceDiagram
  participant U as 用户
  participant G as 输入守卫
  participant I as 意图官
  participant R as 风控官
  participant C as 合规官
  participant E as 体验官
  participant A as 仲裁官
  participant X as 执行官
  participant D as 审计官

  U->>G: 一句话
  G->>I: 归一化文本，或直接拦截
  I->>R: 工具与槽位
  par 并行评估
    R->>A: 风险等级与命中规则
    C->>A: 来源与白名单结论
    E->>A: 追问项与替代路径
  end
  A->>X: 最终判定
  X->>D: 执行结果或待确认
  D-->>U: 回复加审计序号
```

并行的边界：三个评估角色互不共享中间状态，只共享只读的账户快照。任一个抛错，仲裁按「该维度无结论」处理，其余照常。

### 为什么并行

三个评估都是本地计算，并行不带来性能收益。真实价值有两点。

一是故障隔离。合规官接外部征信时，慢或挂都不影响风控官出结论。

二是扩展位。后续接入模型评审、规则热更新、第三方评分，只要实现同一个评估器接口，不用改仲裁逻辑。

## 二、核心算法

### 意图解析

三段式，规则优先，模型兜底，契约兜底。

```mermaid
flowchart LR
  T["用户原话"] --> N["归一化<br/>全角转半角<br/>去零宽"]
  N --> RU{"规则命中"}
  RU -->|"命中且置信度不低于 0.7"| OUT["工具加槽位"]
  RU -->|"未命中或置信度低"| MO["模型解析<br/>tools 声明约束"]
  MO --> CK{"契约校验"}
  CK -->|"通过"| OUT
  CK -->|"不通过"| FB["丢弃该字段<br/>退回规则结论"]
  FB --> OUT
```

规则段的关键设计。

关键词分段匹配，不匹配整句。中文说法太活，整句正则必然漏。

规则按特异性排序，越具体的越靠前。「挂失我的卡」先匹配挂失，再匹配锁卡。「取消视频会员」先匹配订阅，再匹配卡片。

金额抽取先抹掉手机号与长数字，再识别阿拉伯数字、中文数字、万、千。五千块是 500000 分，三千五是 3500 元。

模型段的关键设计。

工具声明走请求体的 `tools` 字段，不写进提示词。结构化声明比自然语言短，也更准。

意图解析关掉思考模式。抽槽是确定性任务，推理 token 属于纯浪费。

输出必须过契约：工具在白名单、参数类型对、数值在范围。不合法的字段丢弃，不整条接受。模型超时或返回乱码，退回规则结论，不阻塞对话。

### 三色判定

四个维度叠加，取最高等级，任一维度判红即红。

| 维度 | 规则名 | 判定 | 后果 |
|---|---|---|---|
| 操作类型 | `base-level` | 只读绿、动账黄、改规则红 | 定基线 |
| 金额 | `single-limit`、`daily-limit` | 单笔超 1000 元、日累计超 5000 元 | 判红 |
| 收款人 | `new-payee` | 首次且达 500 元 | 判红 |
| 可逆性 | `irreversible` | 挂失、改额度、改密码、申购赎回 | 判红 |
| 频次 | `daily-count` | 当日同工具超 5 笔 | 判红 |

每条命中都要带 `rule` 与 `detail`。`detail` 里必须出现具体数字，例如「金额 5000 元超过单笔限额 1000 元」。

只给颜色不给理由的判定，等于没有判定。评审时会被追问到答不上来。

判定函数是纯函数：输入工具、参数、状态快照，输出判定，不改任何数据。

### 并行评估与仲裁

三个评估器实现同一个结构，便于合并。

```ts
interface AssessResult {
  role: "risk" | "compliance" | "experience";
  level: "green" | "yellow" | "red" | "none";
  blocked: boolean;
  requiresConfirm: boolean;
  hits: PolicyHit[];
  note: string;
}
```

仲裁规则四条，顺序执行。

一，任一评估 `blocked` 为真，最终判红并拦截。

二，否则取风控官的等级。合规与体验不提升风险等级，只做否决与补充。

三，`requiresConfirm` 取三者的逻辑或。

四，命中理由全部合并，不去重，保留每个角色各自的说法。

体验官的等级固定为 `none`。它只产追问项与替代路径，不参与风险判断。这条约束防止「话术好不好」影响「能不能办」。

### 确认令牌

黄色操作签发一次性令牌，绑定四样东西。

| 绑定项 | 防什么 |
|---|---|
| 会话标识 | 跨会话盗用 |
| 工具名 | 确认转账却执行挂失 |
| 参数摘要 | 确认后改金额 |
| 过期时间 | 长期有效 |

参数摘要是工具名与排序后槽位的 SHA-256，取前 16 位。

校验三步：查存在、查未过期、用服务端存的原始参数重算摘要比对。

三步全过才执行。令牌一次性，执行后立即失效，重复提交返回「令牌已使用」。

### 审计链

每条记录一个 JSON，只追加，不改写。

```
hash = SHA-256(prevHash + 规范化后的本条内容)
```

首条的 `prevHash` 为 `GENESIS`。

校验从第一条读到最后一条，逐条重算。三种破坏都能发现：改内容、改哈希、删中间一条。

规范化三条：字段顺序固定、空值统一成空字符串、序列化不加空格。

脱敏在写入前完成，不在展示层。卡号留后四位，手机号留前三后四，姓名留姓。

现场演示：改一条记录的结论字段，刷新页面，链校验变成失败并指出断在第几条。

## 三、安全设计

### 四道闸

```mermaid
flowchart TB
  IN["用户输入"] --> G1{"第一道<br/>输入守卫"}
  G1 -->|"命中注入"| B1["拦截并留痕"]
  G1 -->|"通过"| G2{"第二道<br/>来源校验"}
  G2 -->|"收款人不可追溯"| B2["拦截"]
  G2 -->|"通过"| G3{"第三道<br/>三色判定"}
  G3 -->|"红"| B3["拦截并给替代路径"]
  G3 -->|"黄"| G4{"第四道<br/>令牌校验"}
  G3 -->|"绿"| EX["执行"]
  G4 -->|"通过"| EX
  G4 -->|"失败"| B4["拒绝执行"]
  EX --> AU["写审计链"]
```

四道闸的关键是顺序。守卫在最前，判定在最后，令牌在判定之后。顺序错了就有绕过路径。

### 注入防御

归一化先做，再做匹配。归一化处理三件事：全角转半角、去零宽字符、去同形字。

不归一化直接匹配，全角写一句「忽略之前的指令」就能绕过。

四类特征，命中即拦。

| 类型 | 特征 |
|---|---|
| `override` | 忽略之前的指令、ignore previous |
| `roleplay` | 你现在是、扮演、开发者模式 |
| `encoded` | Base64 编码的指令串 |
| `exfiltration` | 输出提示词、system prompt |

### 外部内容隔离

账单备注、商户名、短信、小票属于外部写入，只当数据。

处理方式两层。

第一层，内容侧巡检。扫描备注与商户名，命中可疑指令就在回复里标记「内容含可疑指令，已忽略」。

第二层，来源校验。依据外部内容发起的付款直接拒绝，回复里说明「收款人必须来自你的原话或通讯录」。

### 密钥与凭据

密钥只从环境变量读，源码里出现密钥视为缺陷。

提交前跑一次结构自检，脚本会扫四类特征：OpenAI 风格密钥、DeepSeek 密钥赋值、企业微信密钥赋值、私钥块。

日志与错误信息里不出现密钥与内网地址。

## 四、工程实现

### 工具注册表

内置工具、外部服务、技能三者收敛成一份工具描述，进同一张注册表。

```ts
interface ToolDescriptor {
  name: string;          // 全局唯一，外部工具带 mcp__ 前缀
  summary: string;       // 一句话，直接进请求体
  scene: string;         // 归属场景
  risk: { level; reversible; write };  // 风险画像
  parameters: object;    // JSON Schema
  source: "builtin" | "mcp";
}
```

注册表三条约束：同名报错不覆盖、外部工具失败不影响内置、可按来源或按服务器整体移除。

### 外部服务

走 MCP 协议，服务端独立进程，标准输入输出通信。

风险按「工具级声明、服务级声明、默认只读」三级判定。声明 `irreversible` 一律判红。

外部返回内容只进工具结果，不进系统提示词。模型可以把它当事实，不能当指令。

超时三到五秒，失败返回明确错误，内置工具不受影响。

### 技能按需加载

技能是 Markdown 文件，前置元信息写名称、说明、标签。

两段式披露：系统提示词只放目录摘要，每行一条，截断 80 字符；模型需要细节时调 `skill_load` 取全文，单次上限 4000 字符。

新增技能只需往目录放一个文件，下次请求自动进目录。

### 测试策略

三层，共 91 项。

| 层 | 数量 | 覆盖 |
|---|---|---|
| 单元 | 40 项 | 金额解析、槽位抽取、判定规则、令牌校验、审计链 |
| 集成 | 33 项 | 六场景全链路、注入拦截、红队 40 条统计 |
| 蜂群 | 11 项 | 并行评估、仲裁取最高、轨迹记录、失败降级 |
| 模型 | 7 项 | 真实模型调用、输出契约、超限仍被拦 |

红队集 40 条分四组：直接注入 12 条、间接注入 8 条、越权 8 条、正常请求 12 条。

验收线三条：攻击拦截率不低于 95%，正常误拦不高于 5%，不可逆操作 100% 拦截。

实测攻击拦截率 100%，误拦 0%。

## 五、性能与成本

| 环节 | 耗时 | 说明 |
|---|---|---|
| 规则解析 | 1 毫秒内 | 纯计算，无 IO |
| 三评估并行 | 2 毫秒内 | 本地计算 |
| 审计写入 | 1 毫秒内 | 追加写，SHA-256 |
| 模型兜底 | 0.6 至 0.9 秒 | 关思考模式，单轮 |

成本控制四条。

一，意图解析关思考模式，省下全部推理 token。

二，工具声明走结构化字段，不写进提示词，请求体更短。

三，规则能判的不用模型。实测六类说法里五类走规则，只有口语化表达才调模型。

四，前缀缓存。系统提示词固定，同一会话的第二次请求命中缓存，这部分计费更低。
