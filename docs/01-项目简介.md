# 项目简介

一句话：面向金融的蜂群多智能体系统，让七个角色分工完成一次银行事务，从听懂到办完全程可追溯。

## 一、为什么需要蜂群

传统银行智能体是一个大脑包办所有事。听懂诉求、判断风险、执行操作、记录流水，全在一个函数里。

这种结构有三个问题。

第一，判不准。同一个模型既要想「用户要什么」，又要想「这事能不能办」，两件事互相干扰。

第二，说不清。出了错只能看到一个结论，不知道是哪一步出的问题。

第三，改不动。要加一条风控规则，得动主流程；要加一句合规校验，还得动主流程。

蜂群把一件事拆给多个专职角色。每个角色只做一件事，结论汇到仲裁者。判错了能定位到角色，改规则只改一个角色的代码。

## 二、七个角色

系统由七个角色智能体组成，按顺序协同。

| 角色 | 职责 | 输出 |
|---|---|---|
| 意图官 | 听懂用户要办什么，抽出工具与参数 | 工具名、槽位、缺失项 |
| 风控官 | 按策略判风险等级 | 绿黄红、命中规则 |
| 合规官 | 查来源可信度、工具白名单 | 放行或拦截 |
| 体验官 | 判断还需补什么、该怎么说 | 追问项、替代路径 |
| 仲裁官 | 合并三份评估，取最高风险 | 最终判定 |
| 执行官 | 按判定拦截、待确认或直接执行 | 执行结果 |
| 审计官 | 写入哈希链，形成可校验流水 | 审计序号与摘要 |

前三个评估角色并行工作，互不阻塞。任一个失败只是少一份结论，不拖累其余。

## 三、一次对话怎么走

以「转给小王 100 元」为例。

```
用户说：转给小王 100 元
  ↓ 输入守卫：归一化、注入特征识别
  ↓ 意图官：落到 transfer，槽位 payee=小王 amountCents=10000
  ↓ 并行三评估
      风控官：基础等级黄 + 首次收款人 → 黄
      合规官：收款人在原话中出现，工具在白名单 → 放行
      体验官：金额已给，无需追问
  ↓ 仲裁官：绿、绿、黄取最高 → 黄，需确认
  ↓ 执行官：签发一次性令牌，120 秒有效
  ↓ 用户点确认：校验令牌、重算参数摘要
  ↓ 执行官：扣账
  ↓ 审计官：写链，序号递增，前序哈希串起来
```

七步，每一步都留痕。界面上能看到七个角色的结论与耗时。

## 四、六个场景

| 场景 | 代表说法 | 工具 |
|---|---|---|
| 智能转账 | 转给小王五百、定时下周给房东转房租 | `transfer`、`schedule_transfer`、`create_aa` |
| 账单分析 | 这个月钱花哪了、有没有异常交易 | `analyze_bills` |
| 理财操作 | 有什么稳健产品、赎回稳盈货币 | `wealth_list`、`wealth_risk`、`wealth_purchase`、`wealth_redeem` |
| 卡片管理 | 卡丢了、额度调到两万、申请新卡 | `list_cards`、`lock_card`、`report_loss`、`adjust_limit`、`apply_card` |
| 订阅代扣 | 我订了哪些、什么时候扣费、退掉视频会员 | `list_subscriptions`、`subscription_reminder`、`cancel_subscription` |
| 跨场景联动 | 帮我准备生日、锁定一千、订个蛋糕 | `birthday_lock`、`birthday_book` |

六个场景全部打通，共 21 个内置工具，另有 13 个外部工具通过 MCP 接入。

## 五、三条硬门槛怎么满足

### 权限分级

三色判定，四个维度叠加：操作类型、金额、收款人、可逆性。

绿色直接执行，黄色签发一次性确认令牌，红色直接拦截并给替代路径。

每条判定都带规则名与一句人话说明。界面上点开气泡能看到命中了哪条规则、阈值多少。

### 幻觉防护与注入防御

数字只来自工具返回，模型不产数字。

模型只负责产意图，输出必须过契约校验：工具在白名单、参数类型正确、数值在范围。任何一项不过，丢弃该字段而不是整条接受。

输入先归一化再匹配注入特征。全角、零宽、同形字都处理。命中即拦，不进意图解析。

外部内容（账单备注、短信、小票）只当数据。依据外部内容发起的付款直接拒绝。

### 意图理解与任务规划

规则优先，模型兜底。

规则覆盖六类说法与常见歧义。规则判不出或置信度低时才调模型。

缺槽位时进追问状态，把已抽到的槽位存成草稿，下一轮只补缺的部分。

## 六、渠道

三条通道，共用同一套运行时。

| 渠道 | 用途 | 状态 |
|---|---|---|
| Web 控制台 | 对话、判定、确认卡片、协作轨迹、审计列表 | 可用 |
| 通用 webhook | 对接飞书、钉钉、自建 IM | 可用 |
| 企业微信 | 应用消息收发 | 需凭据，无凭据时 dry-run |

## 八、技术底座

运行时用 TypeScript，Node 22 直接执行，无编译步骤。

前端用 Vue 3 加 Vite，单页控制台。

工具层是自研 harness：内置工具、外部服务、技能三者收敛成统一描述符，进同一张注册表，模型看到一份合并后的工具集。

外部能力走 MCP 协议，服务端独立进程，超时与失败隔离，不影响内置工具。

## 九、边界

系统不含真实银行接口，账户、账单、产品均为合成数据。

外部服务的汇率、征信、费率是演示值，不能用于真实业务。

安全设计参考生产实践，不构成合规认证。
